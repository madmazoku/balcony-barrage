# Автоматические релизы по тегам — задание фазы 7
Статус 2026-11-09: проект решения по запросу владельца; нового release-workflow ещё нет. Реализация и проверка вместе с самостоятельными Windows/Android сборками, с отдельной приёмкой. Владелец спросил о push тега x.y.z / x.y.z-short_desc с исполняемыми файлами и Web-версией на Pages.

## Что работает сейчас
.github/workflows/web-pages.yml автоматически запускает проверки и Web-экспорт для PR в master. После приёмки и merge push в master повторяет проверки, экспортирует и разворачивает Pages. Вручную ничего не собирается и workflow_dispatch отсутствует. Feature-ветки не публикуются. Главная страница: https://madmazoku.github.io/balcony-barrage/ .

## Результат будущего workflow
Push одного нового тега, например 1.2.3 или 1.2.3-demo, запускает сборку именно коммита тега:
- balcony-barrage-<tag>-windows-x86_64.zip — исполняемая игра и нужные файлы, без редактора.
- balcony-barrage-<tag>-android.apk — устанавливаемый APK с постоянной подписью.
- balcony-barrage-<tag>-web.zip — полная Web-сборка для HTTP/HTTPS сервера.
- SHA256SUMS.txt и метаданные с тегом, полным commit SHA, версией Godot и идентификатором сборки.
GitHub Release носит имя тега, содержит все три готовых файла, контрольные суммы, описание и ссылку «Играть». AAB для Google Play не заменяет устанавливаемый APK; добавляется только при отдельной задаче.

Формат: x.y.z или x.y.z-short-desc; валидировать до сборки, не использовать необработанный тег как shell-команду или путь. Значение short_desc в запросе — описание суффикса; буквальный underscore возможен в Git-теге, но не соответствует строгому SemVer. Если он нужен, разрешить как явное расширение формата. Суффикс означает предварительный выпуск (prerelease), не делать его автоматически последней стабильной версией. Тег без суффикса — стабильный выпуск. Отклонять пустой суффикс, разделители путей и неправильные/ведущие нули в номерах.

## Порядок и контроль приёмки
1. Триггер push.tags, фильтр плюс строгая проверка формата. Полная история для проверки ancestry.
2. Коммит тега должен принадлежать принятому master. Теги feature-веток не обходят приёмку. Наличие коммита в master — технический критерий действующего процесса приёмки; не заменять его простым совпадением номера версии.
3. Проверки и импорт проходят до публикации. Использовать общую проверенную процедуру, не плодить две расходящиеся копии установки Godot/проверок.
4. Godot 4.7.2 и export templates той же версии, проверка официальных контрольных сумм. Версию конкретной сборки брать из тега без изменения исходного коммита: в рабочей копии CI задать application/config/version. Полная строка тега отображается в игре, числовые поля Windows получают x.y.z, Android version/name — полный тег, version/code — возрастающий номер сборки.
5. Собрать Windows, Android и Web. Дождаться всех трёх, проверить состав и хеши, затем создавать Release. Не публиковать молча неполный набор.
6. Повторный запуск для того же тега должен безопасно продолжать незавершённый выпуск, а не создавать дубликат. Не перемещать тег и не заменять готовые файлы другим содержимым без решения владельца.
7. Публикацию выполнять разрешёнными contents:write, pages:write, id-token:write только в соответствующих заданиях. Доступ на запись и секреты не выдавать непроверенным PR. Теги сейчас не создавать ради пробы без отдельной приёмки готовой автоматизации.

## Pages: текущая и конкретные версии
Сохранить нынешнюю главную страницу как последнюю принятую сборку master. Для тегов добавить /releases/<tag>/ и список доступных версий со ссылками на скачивание. Старый тег не должен откатывать главную страницу. Обновление master не должно удалять ранее размещённые версии.
У Pages один публикуемый сайт: архив версий нужно собирать целиком при каждом развёртывании. Предлагаемый источник архивов — опубликованные web.zip из GitHub Releases, с проверкой метаданных/хешей; данные не зависимы от временного кеша runner. Новая версия включается в тот же пакет сайта. Публикации master и тегов используют одну очередь (concurrency group для всего сайта), чтобы не затирать друг друга. Путь каждой версии содержит полный тег, нельзя использовать только x.y.z, теряя суффиксы.
Опубликованный сайт ограничен 1 ГБ. Контролировать размер до deploy; при превышении останавливать публикацию с понятной причиной. Не удалять старые версии автоматически без согласованной политики хранения. Вложения Releases остаются доступными независимо от списка версий, размещённых на Pages.

## Android и подпись
Потребуются JDK, Android SDK/build-tools и Android export templates; инструменты CI можно установить независимо от локального Visual Studio. Для устанавливаемых обновлений один постоянный keystore и package ID. Ключ, alias и пароли — в GitHub Secrets, не в репозитории, артефактах и логах. Отдельно согласовать создание/резервную копию ключа перед первым настоящим выпуском. В CI формировать временные export credentials, затем удалять. Случайный новый debug-ключ на каждом запуске не подходит для обновления ранее установленной игры.

## Приёмка автоматизации
На принятом коммите проверить правильный тег и отказ неправильному/непринятому. Проверить три вложения и их SHA256, имя/версию в каждой сборке, Windows без редактора, установку и обновление APK тем же ключом, Web по ссылке версии. Проверить повторный запуск, порядок стабильных/prerelease выпусков, сохранение старой версии после новой публикации master и отсутствие отката главной при старом теге. Физическая проверка телефона — владельцем, не заменяется успешным экспортом.
